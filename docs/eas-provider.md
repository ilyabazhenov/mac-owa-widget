# Провайдер Exchange ActiveSync

Как устроен календарный провайдер `.eas`, по какому протоколу он работает и какие
решения в нём приняты намеренно.

Код: `OWAWidget/Providers/EAS/`.

## Зачем он нужен

OWA-провайдер обращается к `/owa/service.svc` и `/EWS/Exchange.asmx`. В типовой
корпоративной установке эти пути закрыты снаружи, поэтому виджет работает только за
VPN. Проверено на конкретном сервере: и снаружи, и изнутри открыт **ровно один**
путь — `/Microsoft-Server-ActiveSync`, тот самый, которым синхронизируются телефоны.

Отсюда и весь замысел: тот же почтовый ящик, другой протокол, VPN не нужен.

Аккаунты типа `.owa` продолжают работать как раньше. Типы сосуществуют, выбор — при
добавлении аккаунта.

## Протокол

### Транспорт

Одна точка входа, всё остальное — параметры:

```
POST https://<host>/Microsoft-Server-ActiveSync
     ?Cmd=<команда>&User=<DOMAIN\user>&DeviceId=<32 hex>&DeviceType=<строка>

Authorization:        Basic base64(user:password)
MS-ASProtocolVersion: 14.1
X-MS-PolicyKey:       <получен при Provision>
Content-Type:         application/vnd.ms-sync.wbxml
```

Аутентификация — **Basic**, в отличие от NTLM у OWA-клиента. Это важно для защиты
учётной записи, см. ниже.

### WBXML

Тело запроса — не XML, а WBXML 1.3: имена тегов сжаты в однобайтовые токены, смысл
которых зависит от **текущей кодовой страницы**. Переключение страницы — служебный
байт `0x00` плюс номер.

Следствие, определяющее устройство кодека: один и тот же байт означает разное на
разных страницах. `0x08` — это `Set` на странице 18 и `PolicyType` на странице 14;
`Status` живёт на четырёх страницах сразу. Поэтому поиск по дереву сопоставляет
**пару «страница + токен»**, а не имя:

```swift
node.child(PR.status)    // Status на странице 14
node.child(ST.status)    // Status на странице 18 — другой узел
```

Поиск по имени молча возвращал бы не тот узел. Это не гипотетическая опасность: один
запрос `Provision` трогает две страницы, календарный `Sync` — четыре.

Пример: тело `FolderSync` целиком, 13 байт.

```
03 01 6a 00     заголовок: WBXML 1.3, UTF-8, пустая таблица строк
00 07           SWITCH_PAGE → страница 7 (FolderHierarchy)
56              FolderSync, бит 0x40 = «с содержимым»
52              SyncKey
03 "0" 00       строка inline
01 01           два END
```

### Команды

| Команда | Зачем |
|---|---|
| `OPTIONS` | доступность и проверка пароля, одним запросом без тела |
| `Provision` | согласование политики безопасности, выдаёт `PolicyKey` |
| `FolderSync` | список папок; календарь — это `Type = 8` или `13` |
| `Sync` | элементы: чтение, создание, дозагрузка (`Fetch`) |
| `MeetingResponse` | ответ на приглашение |
| `Search` | поиск людей по адресной книге |
| `Settings` | собственный SMTP-адрес пользователя |
| `ResolveRecipients` | занятость коллег |

### Provision: две фазы

Обязательная процедура, без неё `Sync` отвечает `449`.

1. Запрос политики. **Обязан содержать блок `settings:DeviceInformation`** и
   именно **перед** `Policies` — иначе Exchange 2010+ отвечает `Status=165`
   (`DeviceInformationRequired`). В ответе — временный `PolicyKey`.
2. Подтверждение политики с этим ключом и `Status=1`. В ответе — рабочий `PolicyKey`
   для всех последующих команд.

Клиент принимает политику так же, как это делает любой телефон. Если политика
предусматривает удалённое стирание, администратор формально получает такую
возможность в отношении зарегистрированного устройства.

### Sync: цепочка ключей

`Sync` не знает понятия «диапазон дат». Он отдаёт **изменения** относительно
`SyncKey`, а сервер ведёт эту цепочку на пару «устройство + коллекция».

```
SyncKey=0  →  ответ без данных, выдаёт рабочий ключ
SyncKey=N  →  Add / Change / Delete + новый ключ
              MoreAvailable → повторить с новым ключом
```

Первый раунд **никогда не несёт элементов** — он только устанавливает ключ. Считать
его пустой ответ за «календарь пуст» значит не показать ничего до первого изменения.

`Status=3` означает, что сервер ключ забыл. Всё, что он пришлёт дальше, — дельты
относительно базы, которой у нас больше нет, поэтому локальная копия выбрасывается
вместе с ключом, и цепочка начинается заново.

## Архитектура

```
CalendarService  (@MainActor)
      │  CalendarProvider — 8 методов, контракт не менялся
EASCalendarProvider  (actor)
      │
EASSessionRegistry  (actor, shared)  ──► EASAccountSession  (actor)
                                              ├── EASClient          транспорт и команды
                                              ├── EASSyncStore       SyncKey + сырые элементы
                                              └── EASRecurrenceExpander
```

### Почему сессия живёт в реестре

`CalendarService.rebuildProviders()` выбрасывает провайдеры и строит новые — при
запуске, при любой правке аккаунта, при повторном доверии сертификату. А цепочка
`SyncKey` на сервере при этом не сбрасывается.

Сессия, созданная вместе с провайдером, означала бы две сессии на одну цепочку. Это
не даёт ошибки — они **поделят изменения между собой**, и часть встреч просто не
появится. Поэтому сессия живёт в `EASSessionRegistry` и переживает пересборку.

Ключ реестра — `accountID` плюс отпечаток креденшелов (SHA-256 от адреса сервера,
логина, пароля и полей устройства). Пароль не хранится: отпечатка достаточно, чтобы
понять, что аккаунт изменился и сессию надо пересоздать.

### Инвариант снимка

> `SyncKey` и элементы пишутся и читаются **атомарно**. Если элементы не прочитались,
> ключ выбрасывается тоже.

Ключ — это обещание серверу «всё до этого места у меня есть». Ключ без элементов хуже
отсутствия ключа: каждая последующая синхронизация вернёт небольшую дельту, календарь
останется пустым навсегда, и **нигде ничего не сообщит об ошибке**.

Реализовано через `policy: .treatAsEmpty` — нечитаемый контейнер возвращает `nil`
целиком, а не по частям.

### Экономия записи

Снимок перезаписывается только когда элементы реально изменились. Большинство проходов
по таймеру не приносят ничего, а запись шифрует и кладёт на диск весь календарь.

Пропуск безопасен: на диске остаётся пара, снятая одновременно, то есть
согласованная. После перезапуска синхронизация пойдёт от сохранённого ключа, и сервер
повторит ровно те изменения, которых не было.

## Отображение методов

| `CalendarProvider` | Команды EAS |
|---|---|
| `fetchEvents` | `Provision` → `FolderSync` → `Sync` в цикле + раскрытие повторов |
| `validateCredentials` | `OPTIONS` → `Provision` → `FolderSync` |
| `respondToMeeting` | `MeetingResponse` |
| `fetchDetails` | из локальной карты; `Sync Fetch` только при обрезанном теле |
| `findPeople` | `Search` со `Store=GAL` |
| `resolveOrganizerSMTPEmail` | `Settings` → `UserInformation` |
| `getUserAvailability` | `ResolveRecipients` + `Options/Availability` |
| `createMeeting` | `Sync Add` с коллекцией `Attendees` |

### Проверка соединения делает четыре запроса, а не один

Проверка, дёргающая только `OPTIONS`, прошла бы и на ящике с выключенным ActiveSync —
пользователь узнал бы об этом позже, пустым календарём. Поэтому проверяется вся
цепочка до календарной папки включительно.

Неверный пароль по-прежнему стоит одной попытки: клиент латчится на первом `401`, и
остаток цепочки до сети не доходит.

### Созданную встречу нужно забирать явно

ActiveSync **не присылает обратно** элемент, созданный этим же устройством: `ServerId`
выдан в ответе на `Add`, и сервер считает, что устройство про него знает.

Поэтому после создания элемент запрашивается отдельным `Sync Fetch`. Без этого встреча
существует на сервере и в OWA, но в виджете не появляется до полной
пересинхронизации.

### Занятость: позиционная гарантия

`ColleaguePresenceService` сопоставляет строки с запрошенными адресами **по позиции** и
считает несовпадение количества сбоем обновления.

Сервер вправе пропустить адрес, который не смог разрешить. Поэтому строк всегда ровно
столько, сколько адресов запрошено, в том же порядке, а пропуски заполняются кодом `4`
(«нет данных»). Выбросить строку значило бы сдвинуть каждого следующего коллегу на
чужое расписание.

## Раскрытие повторяющихся встреч

Сервер присылает **правило** и список исключений, но никогда сами экземпляры. Всё, что
виден календарь для серии, производится на клиенте — страховки со стороны сервера нет.

### Таймзоны

Серия повторяется по **настенному времени**. «Каждый вторник в 10:00» — это 10:00 там,
где организатор, а через переход на летнее время это другой момент в UTC. Поэтому
разбирается блоб `calendar:Timezone` — base64 от 172-байтной структуры Win32
`TIME_ZONE_INFORMATION` с правилами вида «последнее воскресенье марта».

Для зон без перехода (вся Россия с 2014 года) правила отсутствуют, и расчёт
вырождается в постоянное смещение.

### Три места, где такие раскрыватели ломаются

Каждое закрыто тестом в `EASRecurrenceTests`:

1. **Маска дней недели — это маска, а не день.** `62` означает «любой будний», и
   правило «первый рабочий день месяца» обязано работать, а не превращаться в «первый
   понедельник».
2. **31-е число есть не в каждом месяце.** Нормализация даты перекинула бы встречу на
   1-е следующего, то есть выдумала бы встречу, которой в Exchange нет. Месяц
   пропускается.
3. **Перенесённый экземпляр, чей исходный слот не сгенерирован.** Организатор двигает
   одну встречу за пределы серии — и она исчезает бесследно. Такое исключение
   выдаётся отдельно.

Плюс жёсткий потолок в 2000 экземпляров: правило без `Until` и без `Occurrences` —
«каждый будний день, бессрочно» — совершенно легально, и без потолка крутится до
убийства процесса прямо на пути синхронизации.

### Идентичность экземпляра

Экземпляр опознаётся по **исходному** времени слота, а не по фактическому:

```
id = "<ServerId>|<эпоха исходного старта>"
```

Перенос одной встречи не меняет её id. На стабильности id держатся дедупликация в
`CalendarService`, оптимистичное обновление RSVP и кэш деталей — при смене id все три
ломаются молча.

### Отбраковка перед раскрытием

Календарь за годы накапливает тысячи прошедших встреч, а окно виджета — это
`[-7 дней, +30 дней]`. Раскрывать каждый элемент, чтобы затем выбросить почти все,
значит платить за всю историю на каждом проходе.

`mayProduceOccurrences` отсеивает заведомо невозможное сравнением дат. Проверка
намеренно осторожная: сомнение трактуется в пользу раскрытия, потому что пропустить
встречу — это потерять её из календаря, а лишний раз раскрыть — потратить
микросекунды. Перенесённые экземпляры проверяются отдельно.

## Защита учётной записи

Самый опасный участок, и единственный, способный навредить пользователю, а не фиче.

Basic-аутентификация отправляет пароль в **каждом** запросе, а один `fetchEvents` — это
2–4 запроса. Наивная реализация дала бы 6–8 неудачных попыток до срабатывания автомата
защиты, при типичном пороге блокировки Active Directory в 3–5.

Два уровня:

1. **Латч внутри `EASClient`.** Первый же `401` взводит флаг, все последующие запросы
   этого клиента падают **не доходя до сети**. `401` не ретраится никогда — ветка
   `449 → provision → повтор` с этого пути недостижима.
2. **Отображение в `OWAError.authenticationFailed`.** Этот случай `CalendarService`
   считает окончательным отказом и латчит автомат с первой ошибки, минуя порог. Для
   Basic это корректно: `401` здесь и есть отказ, в отличие от NTLM, где это челлендж.

Итог — 1–2 попытки на неверный пароль. Восстановление прежнее: автоматическая проба
раз в 30 минут или ручной повтор.

### Ошибку синхронизации нельзя глотать

У сессии есть локальная карта, и соблазн при сбое сети вернуть её из `fetchEvents`
велик. Так делать нельзя: решение «мы офлайн» принимает `CalendarService`, и ему нужен
брошенный наружу сбой, чтобы поставить `.offlineCached`, **не тронуть кэш** и накормить
автомат защиты.

Проглоченная ошибка выглядит как успешная синхронизация: статус соврёт `.lastSynced`,
кэш перезапишется, а пользователь не узнает, что связи нет. От этого же кэша
планируются напоминания — встреча в 10:00 должна напомнить о себе, даже если интернет
пропал в 9:00.

## Профиль устройства

Пять полей, которыми клиент представляется серверу, редактируются в настройках
аккаунта, раздел «Дополнительно»:

| Поле | Куда уходит |
|---|---|
| `DeviceType` | параметр URL |
| `User-Agent` | HTTP-заголовок |
| `Model`, `FriendlyName`, `OS` | блок `settings:DeviceInformation` |

Аттестации устройства в ActiveSync нет — всё это самодекларация. Но поля не
декоративные: Exchange умеет ограничивать доступ правилами
`New-ActiveSyncDeviceAccessRule` по `DeviceType`, `DeviceModel`, `DeviceOS` и
`DeviceUserAgent`, а администратор видит их в `Get-MobileDevice`. Редактируемость нужна
на случай, когда организация пропускает только известные типы устройств.

**`DeviceId` редактированию не подлежит.** Он генерируется один раз и хранится отдельно
от снимка синхронизации. Новый идентификатор — это не мелочь: он регистрирует в Exchange
отдельное устройство, которое видит администратор, которое считается в квоту устройств
ящика и которое в организациях с правилами Allow/Block/Quarantine может попасть в
карантин с уведомлением админу. По нему же сервер ведёт цепочку `SyncKey`.

Поэтому при нечитаемом контейнере идентификатора код **бросает ошибку, а не выпускает
новый**.

## Таблицы токенов: что проверено

Ошибка в токене **запроса** не даёт ошибки — она даёт молча отсутствующее поле.
Поэтому степень достоверности таблиц зафиксирована в коде:

| Страница | Что это | Статус |
|---|---|---|
| 0 AirSync, 7 FolderHierarchy, 14 Provision, 18 Settings | | проверены на живом сервере |
| 4 Calendar, 17 AirSyncBase | | сверены с опубликованной спецификацией |
| 2 Email, 8 MeetingResponse, 10 ResolveRecipients, 15 Search, 16 GAL | | **восстановлены по памяти** |

Страницы спецификации для последних пяти не отдаются через веб, репозиторий исходников
закрыт. Проверяются они эмпирически.

### Как проверить таблицу

Клиент сам находит в каждом ответе токены, которых не знает, и пишет их имена в
диагностический лог:

```
EAS ResolveRecipients unmapped tokens: p10_0x16, p10_0x19
```

`pN_0xNN` — это страница и код токена. Их появление означает поле, которое пришло и было
выброшено. Имя токена — идентификатор протокола, персональных данных в нём нет, поэтому
его безопасно писать открытым текстом.

Незамапленные токены в ответах `Provision` и `Settings` — норма: это поля политики
безопасности (`EASProvisionDoc`), которые мы намеренно не разбираем.

Для **записи** дампа недостаточно — нужен round-trip: записать значение, перечитать
свежим `Sync`, сравнить. Для `MeetingResponse` — ответить и убедиться, что
`calendar:ResponseType` изменился.

## Диагностика

```bash
make diag     # текущая и предыдущая сессии, открытым текстом
```

Читает `~/Library/Application Support/OWAWidget/diagnostic.log`.

**`make logs` для этого не годится.** Он читает унифицированный лог, а macOS не
сохраняет уровень `.info` на диск: `log show` не найдёт ничего постфактум. Он полезен
только вместе с живым `log stream`.

Что пишется:

```
CalendarService providers rebuilt count=1 accounts=1 types=eas
EAS Provision http=200 bytes=264
EAS Provision unmapped tokens: p14_0x0E, p14_0x0F, ...
EAS sync done items=1540 rounds=1 changed=false
EAS created event serverId=20:1541 attendees=2
EAS meeting response sent occurrence=true
```

Полное дерево ответа пишется в зашифрованный трейс `easclient.log` (только в
DEBUG-сборке) — там темы встреч и адреса, поэтому открытым текстом ему нельзя.

## Ограничения

**Общие и делегированные ящики.** ActiveSync работает строго с одним почтовым ящиком.
Открыть календарь коллеги или общий ящик нельзя — это умеют EWS и MAPI. Обойти на EAS
невозможно.

**Создание серий не предлагается.** Для этого нужны настоящие правила переходов на
летнее время в блобе, а восстановить их из `TimeZone` нельзя. Одиночные встречи
создаются с абсолютным UTC-временем, и упрощённого блоба им достаточно.

**`FilterType = 5`.** Синхронизируется последний месяц календаря, а будущие события и
бессрочные повторяющиеся серии Exchange присылает независимо от фильтра. При смене
значения локальная цепочка `SyncKey` сбрасывается и создаётся заново, чтобы сервер и
виджет согласовали новое окно.

**Отправка приглашений не подтверждается.** Элемент с участниками и `MeetingStatus = 1`
заставляет Exchange разослать приглашения, но отдельного шага «отправить» в протоколе
нет. Успешный статус означает, что запрос принят, — дошли ли приглашения, видно только
в чужом ящике.

**Регистрация устройства видна администратору.** Первое подключение создаёт запись с
указанным `DeviceType`. В организациях с правилами ABQ она может попасть в карантин и
породить уведомление. Это вне контроля приложения.
