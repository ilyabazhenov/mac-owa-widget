# Бэкап и восстановление Sparkle EdDSA ключа

Инструкция по резервному копированию приватного ключа, которым подписываются
обновления OWAWidget, и по его восстановлению на новой машине.

## Почему это критично

Sparkle проверяет каждое обновление EdDSA-подписью. Публичный ключ зашит в
`Info.plist` (`SUPublicEDKey`) **той версии, которую пользователь уже установил**.
Обновление, подписанное другим ключом, будет отвергнуто молча.

Потеря приватного ключа означает, что выпускать обновления существующим
пользователям станет невозможно навсегда — единственный выход будет попросить
всех переустановить приложение вручную.

Публичный ключ проекта (не секрет, служит для проверки):

```
WPYI42Z1jbfBdFNmyBey6tOcbWyU1x6GGVlmn/nNY/I=
```

Источник истины — `OWAWidget/Info.plist`, ключ `SUPublicEDKey`.

## Где ключ находится сейчас

В login Keychain на машине разработчика:

- Служба (`svce`): `https://sparkle-project.org`
- Аккаунт (`acct`): `ed25519`

Оттуда его читают `sign_update` и `generate_appcast` во время
`make release-package`. Никакой другой рабочей копии нет.

## Сделать бэкап

Оба способа выводят приватный ключ. Выполняй их сам, в своём терминале, и не
вставляй результат в чаты, тикеты и историю команд.

### Способ A — штатный экспорт Sparkle (рекомендуется)

```bash
.build/artifacts/sparkle/Sparkle/bin/generate_keys -x ~/Desktop/sparkle-owawidget-private.key
```

Keychain может спросить разрешение на доступ — это нормально, надо разрешить.
Файл появится на рабочем столе. Перенеси его содержимое в менеджер паролей и
затем удали файл:

```bash
rm -P ~/Desktop/sparkle-owawidget-private.key
```

### Способ B — напрямую из Keychain

```bash
security find-generic-password -s "https://sparkle-project.org" -a ed25519 -w
```

Печатает base64-строку приватного ключа в терминал, без промежуточного файла.

## Куда класть бэкап

- Менеджер паролей (1Password / Bitwarden / iCloud Keychain), запись с понятным
  именем вроде `OWAWidget Sparkle EdDSA private key`.
- Рядом с записью сохрани публичный ключ из этого документа — по нему потом
  можно проверить, что восстановлен именно нужный ключ.

**Что бэкапом не является:** GitHub Actions Secret. Секреты GitHub нельзя
прочитать обратно ни через веб-интерфейс, ни через API — только перезаписать.
Как копия для восстановления он бесполезен.

## Проверить, что бэкап правильный

Не восстанавливая ничего, сверь публичный ключ, который соответствует ключу в
Keychain, с тем, что зашит в приложение:

```bash
.build/artifacts/sparkle/Sparkle/bin/generate_keys -p
```

Вывод должен совпасть с `SUPublicEDKey` в `OWAWidget/Info.plist` и со строкой в
разделе «Почему это критично» выше. Если совпадает — в Keychain лежит тот самый
ключ, и его экспорт является валидным бэкапом.

## Восстановление на новой машине

1. Установи Xcode и получи исходники проекта.

2. Подтяни бинарники Sparkle (`sign_update`, `generate_appcast`, `generate_keys`):

   ```bash
   swift package resolve
   ```

3. Положи приватный ключ из менеджера паролей во временный файл, например
   `~/Desktop/restore.key`, одной строкой без лишних переводов строки.

4. Импортируй его в login Keychain:

   ```bash
   .build/artifacts/sparkle/Sparkle/bin/generate_keys -f ~/Desktop/restore.key
   ```

5. Удали временный файл:

   ```bash
   rm -P ~/Desktop/restore.key
   ```

## Проверить восстановление

**Шаг 1 — публичный ключ совпадает:**

```bash
.build/artifacts/sparkle/Sparkle/bin/generate_keys -p
```

Должен вывести `WPYI42Z1jbfBdFNmyBey6tOcbWyU1x6GGVlmn/nNY/I=`. Если вывелось
что-то другое — импортирован не тот ключ, дальше идти нельзя.

**Шаг 2 — подпись реально работает:**

```bash
echo probe > /tmp/probe.txt && .build/artifacts/sparkle/Sparkle/bin/sign_update /tmp/probe.txt
```

Должна напечататься строка вида `sparkle:edSignature="..." sparkle:length="6"`.
Если строки нет — ключ недоступен для `sign_update`, релиз собирать нельзя.

После этих двух шагов `make release-package` будет подписывать обновления как
раньше.

## Требования к новой машине

Помимо ключа, для выпуска релиза с чистой машины нужно:

- **Xcode** не ниже того, на котором собирался последний релиз. На момент
  написания: Xcode 26.6 (build 17F113), Swift 6.3.3. Более старые версии
  ломаются на зависимости `KeyboardShortcuts` — см. `AGENTS.md`, раздел
  «Релизный процесс».
- **`gh auth login`** — публикация делается через `gh release create`.
- **`swift package resolve`** — подтянет Sparkle и KeyboardShortcuts по версиям,
  зафиксированным в `Package.resolved`.

Отдельного сертификата подписи не требуется: приложение подписывается ad-hoc
(`CODE_SIGN_IDENTITY ?= -` в `Makefile`), терять нечего.

## Если ключа нет и бэкапа не осталось

Восстановить его невозможно — это единственный сценарий, ради которого весь этот
документ существует. Тогда:

1. Сгенерировать новую пару: `scripts/generate_sparkle_keys.sh`
2. Заменить `SUPublicEDKey` в `OWAWidget/Info.plist` на новый публичный ключ
3. Выпустить релиз с новым ключом

Уже установленные копии это обновление **не примут**: у них зашит старый
публичный ключ. Всем пользователям придётся скачать и установить приложение
заново вручную. Авто-обновление для них восстановится только начиная со
следующей версии после ручной переустановки.

## Заметка на будущее

Ключ нужен в двух местах релизного скрипта — `sign_update` подписывает архив, а
`generate_appcast` подписывает запись в `appcast.xml`
(`scripts/package_release.sh`). Оба читают его из Keychain по одним и тем же
служба/аккаунт. Отдельно стоит знать, что `generate_appcast` при недоступном
ключе завершается с кодом 0 и молча пишет appcast без подписи — то есть
неудачная подпись не обязательно заметна по коду возврата.
